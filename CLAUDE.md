# Project Overview: Procedural Web FPS

**Concept:** A lightweight, high-performance web-based multiplayer FPS. It combines the advanced mechanical logic and physics of CS:GO with the simplified geometry of classic CS 1.6 maps, rendered with a highly stylized, procedural "potato-spec" (LodAdj=5) aesthetic.

**Design Philosophy:** Built through first-principles engineering, the project utilizes a zero-dependency, self-contained architecture. The client executes directly in the browser via standard ES Modules—requiring no npm packages, bundlers, WebAssembly, or third-party graphics libraries. Every system is micro-optimized to eliminate garbage collection spikes, minimize input lag, and maximize frame rates.

## 1. Technical Stack

* **Language:** Vanilla JavaScript (ES6 Modules) and standard Web APIs.
* **Graphics:** Pure WebGL2 (Bare-metal rendering).
* **Networking:** WebTransport (HTTP/3 QUIC) for native UDP-like datagram transmission.
* **Map Format:** Direct GoldSrc BSP (Version 30) binary parsing.

## 2. Core Systems & Architecture

### Graphics & Rendering (The "Potato" Aesthetic)

* **Zero-Asset Pipeline:** The game loads exactly zero image or texture files.
* **Procedural Fragment Shaders:** The visual identity emulates the extreme texture-degraded, flat-shaded look of older Radeon GPUs running LodAdj=5. Textures are procedurally generated in the fragment shader using basic math, noise functions, and flat color assignments based on string names (e.g., `metal`, `crate`) extracted from the map file.
* **Single-Draw-Call Geometry:** Map geometry is packed into a single Vertex Buffer Object (VBO) to keep GPU draw calls as close to zero as possible.

### Map Parsing (GoldSrc BSP)

* **Native Binary Reading:** Native `fetch()` and `DataView` APIs are used to read CS 1.6 `.bsp` files directly into JavaScript `Float32Array` and `Int32Array` buffers.
* **Zero-Overhead Memory:** Because the parsed BSP lumps are already loaded into typed arrays, they are passed directly into WebGL2 buffers, bypassing the need for intermediate data structures or mesh conversions.

### Physics & Gameplay Logic (CS:GO Mechanics)

* **Modern Movement on Retro Geometry:** The engine implements CS:GO’s precise movement physics (acceleration, friction, air-strafing) mapped against the simplified collision hulls of CS 1.6 BSP architecture.
* **Strict Memory Management:** All game states, physics calculations, raycasting, and AABB collision sweeps are handled via pre-allocated `Float32Array` object pools to prevent JavaScript garbage collection from interrupting the main loop.

### Networking & Server Sync

* **WebTransport Datagrams:** Replaces WebSockets and WebRTC to provide a direct, low-latency connection without the overhead of STUN/TURN signaling servers.
* **Source-Style Netcode:** Utilizes fixed-tick server logic (e.g., 64-tick), client-side prediction, and server reconciliation, ensuring crisp hit registration that doesn't suffer from TCP head-of-line blocking.
* **Pragmatic Backend:** The server architecture remains lightweight enough to be deployed directly onto custom self-hosted Linux environments (such as DietPi setups or Pterodactyl panels) with minimal overhead.
## Development

* **Runtime:** Deno (≥ 2.9) for the server, static file serving and tests. The WebTransport server uses Deno's unstable QUIC API (`Deno.QuicEndpoint` + `Deno.upgradeWebTransport`), isolated in `server/transport.js`. No npm/jsr packages anywhere.
* **Run:** `deno task start` (env `MAP=de_dust2`), then open `http://127.0.0.1:27015/` (`?team=t|ct&name=…&primary=ak47&secondary=deagle`); `?offline&map=…` plays locally without the server. Each browser tab is one player. TCP 27015 serves HTTP; UDP 27015 carries WebTransport. Clients connect via `127.0.0.1` (not `localhost`) because Chrome tries `::1` first.
* **Test:** `deno task test` (`Deno.test` + `node:assert`; map-dependent tests skip if `maps/*.bsp` is missing). `deno lint` must stay clean.
* **Certificates:** `server/cert.js` auto-generates a 13-day ECDSA P-256 self-signed cert in `certs/` with `openssl`; clients pin it via `serverCertificateHashes` fetched from `/connect.json`.
* **Maps:** `maps/` holds Valve CS 1.6 BSPs — copyrighted, git-ignored, never commit them.
* **File names vs ad blockers:** privacy filter lists block some script URLs by name (`hitbox.js` was blocked as an analytics tracker, freezing the client on load). Avoid names like `hitbox`, `analytics`, `track`, `ads`, `beacon`, `stats` in client-served files.
* **Layout:** `shared/` = code run identically by client and server (BSP parsing, physics, protocol); `client/` = browser only; `server/` = Deno only.
* **Lighting:** the BSP's own lighting lump is packed into one lightmap atlas texture at load time (map data, not an image file); albedo is fully procedural from texture names (`shared/materials.js`).
* **Chrome datagram limit:** `maxDatagramSize` is 1024 bytes — every packet must fit.
* **Movement (`shared/pmove.js`):** Source `FullWalkMove` ordering with CS:GO convars (`MOVE` table). Player origin is the GoldSrc hull *center* (standing hull 32×32×72, duck hull 32×32×36 — fixed by the BSP clipnodes), so eye heights are 64 standing / 30 crouched above the feet. Crouch-jump raises feet 9 units like CS:GO. Stamina constants are approximations, tuned by feel.
* **Collision (`shared/trace.js`):** hull 0 is rebuilt from BSP nodes and appended after the clipnodes; one recursive trace serves all hulls. Solid brush entities are `func_*` minus a non-solid list; `func_ladder`/`func_water` are volumes.
* **Weapons (`shared/weapons.js`):** CS:GO accuracy model (penalty + recovery with the start/end-bullet transition, movement/air inaccuracy, jump/land penalties), spread seeded by the tick/command number, aim punch with CS:GO recoil convars. Fire rates are tick-quantized (AK: 7 ticks/shot at 64 tick), as in CS:GO.
  * **Real game data:** `shared/weapondata.js` is generated by `tools/gen_weapondata.js` from CS:GO's final `items_game.txt` (all 34 guns, primary + alt modes). Never hand-edit it; reload times and HUD labels (not in that file) live in `EXTRA` in weapons.js and are approximate.
  * **Spray patterns:** generated exactly like CS:GO: Valve's `CUniformRandomStream` (bit-exact port) seeded with each gun's `recoil seed`, angle drawn before magnitude, full-auto tables lerp by `weapon_recoil_variance` 0.55, first 4 shots suppressed from 0.75. The formula was confirmed by matching documented spray shapes (AK, Galil, FAMAS, SG 553, MAC-10); tests pin them.
  * **Not yet modeled:** scope/burst/silencer toggles (weapons spawn in their default mode: USP-S and M4A1-S silenced), revolver cocking, Negev's spread tightening, fixed shotgun spread patterns, the camera-only view punch (`weapon_recoil_view_punch_extra`).
* **Breakables (`shared/breakables.js`):** `func_breakable` with GoldSrc semantics: `health`, `material` (missing = glass), spawnflag 1 trigger-only (CS bomb-site crates: bullets do nothing), 256 one-hit melee, material 7 unbreakable. Bullets deal CS:GO damage with range falloff (`damageAtRange`). Each breakable has a slot (1..255, BSP entity order) stored in vertex byte 39; the world vertex shader drops triangles of broken slots via the `u_broken` bitmask, so the world stays one draw call. Broken ones become `ENT_NONE` (no collision), lose their decals and burst into instanced procedural debris (`client/gl/debris.js`). They reset on respawn (round restart). Mapper-built crates are often several overlapping breakables (fy_buzzkill: lid/shell, hollow walls, floor slab) that break separately, as in GoldSrc. Not yet: explosions (`explodemagnitude`), firing `target`, touch/pressure flags, spawned items, bullet penetration.
* **Netcode (Phases 5-6):** `shared/protocol.js` is the binary wire format (v4; preallocated `Writer`/`Reader`, every message ≤ `MAX_DATAGRAM` 1024). Client → server: `HELLO` (resent every 250 ms until `WELCOME`), then `CMDS` every tick with the newest 4 user commands (redundancy) plus the snapshot ack; each command carries `viewTick`, the server tick the player was seeing others at. An empty `CMDS` is the 1 Hz keepalive; `BYE` on page hide frees the player at once (Deno does not surface the browser's session close). Server (`server/game.js`, drift-free 64 Hz loop in `server/main.js`) runs commands through `shared/player.js` (the same code the client predicts with), one per tick plus an 8-command bank, repeating the last one when lost beyond redundancy. Snapshots every tick: own state in full (raw `PlayerState`/`WeaponState` bytes), other players delta-compressed against the client's last ack (`SnapshotRing`, 32 deep), the breakable mask, then the tick's events (world impacts except the receiver's own, blood hits, and kills repeated for `KILL_REPEAT_TICKS`). `INFO` (names/teams) every second and on roster changes.
  * **Prediction/reconciliation (client/main.js):** the client stores its state after every command; each snapshot's own state is compared byte-for-byte with the prediction for `lastCmd`; on mismatch it adopts the server state, replays later commands and blends the visible correction away (`smooth`, 15/s). Respawns are adopted the same way. Must stay bit-exact: `test/server.test.js` checks it through the wire with packet loss; the HUD shows the live exact rate.
  * **Interpolation:** other players render `INTERP_TICKS` (2 = CS:GO `cl_interp_ratio 2`) behind a smoothed server clock, lerped between the two bracketing snapshots. They are drawn as their hitboxes.
  * **Hits and lag compensation (`shared/hitgroups.js`):** four CS:GO hit groups (head ×weapon headshot multiplier, chest 1, stomach 1.25, legs 0.75) as yaw-rotated boxes that squash when crouching. The server keeps 64 ticks of position history and rewinds every target to the shooter's `viewTick` before tracing (`sv_maxunlag` 1 s); the nearer of world and player wins. Damage is truncated like CS:GO; friendly fire is off; the dead respawn after 2 s. The client stops its own bullets at the players it sees but shows hits only when the server's blood events arrive. Hidden tabs keep applying snapshots/events from a timer.
* **Damage (Phase 7a, `shared/player.js`):** `resolveShots` ports CS:GO FireBullet/HandleBulletPenetration: up to 4 penetrations, none beyond 3000 units, TraceToExit within 90 units, loss = 16% of damage + (3 / weapon penetration × 1.25) × (3 / combined modifier) + thickness² / (combined × 24); glass/grate 3.0 (5%), wood-wood/cardboard 3.0, plastic 2.0; range falloff compounds per hit; bullets go through players (12 units of flesh) for collaterals. Surface types (`shared/surfaces.js`) come from CS:GO `surfaceproperties_cs.txt` values via a GoldSrc RecursiveLightPoint face lookup → texture → `shared/materials.js` class. `applyDamage` is CS:GO armor (ratio × 0.5, bonus 0.5, helmet for the head, legs unprotected) plus tagging (`PS_VELMOD`, the weapon's flinch value, recovering 0.4/s — the rate is an approximation; SMGs have 0 = no tagging in the data).
* **Rounds and economy (Phase 7b):** `shared/economy.js` holds CS:GO competitive rules (15 s freeze, 1:55 rounds, 20 s buy time after the freeze, 7 s round end, $800 start / $16000 cap, $3250 win, loss bonus 1400 + 500/streak to 3400 with the 2019 decrement-on-win rule, weapon kill awards, −$300 teamkill), the buy menu and buy zones (`func_buyzone`, else around team spawns). `server/game.js` runs warmup (free respawns, $16000) until both teams have players, then freeze → live → over; survivors keep gear, the dead start with knife + pistol; time expiry wins for CT on bomb maps, T on hostage maps, draw elsewhere; halftime swap after 15, first to 16. Freeze masks input with `FREEZE_BUTTONS` on both sides (prediction). `Game` takes a rules override (tests use short timings or `{ rounds: false }`). Client HUD: `client/hud.js` (B buy menu, Tab scoreboard, money, round bar/banner).
* **The bomb (Phase 7c, `shared/bomb.js`):** bomb sites are `func_bomb_target` brushes (`info_bomb_target`: 256-unit box, approximation), radius from `info_map_parameters` `bombradius` (default 500). The C4 is weapon `c4` in `SLOT_C4` (key 5; `SLOT_GRENADE` 3 is reserved). Planting and defusing run in the shared player simulation (`bombAction` in `shared/player.js`, predicted): plant = C4 in hand + attack + on the ground + touching a site for 3 s; defuse = CT + use, started within 90 units looking at the bomb (cone 0.8, no wall between; reach is an approximation), 10 s or 5 s with the $400 kit (`ITEM_DEFUSER`, `OWN_DEFUSER` in the snapshot); both root the player (`WS_ACTION`/`WS_ACTION_END`) and report `WEV_PLANTED`/`WEV_DEFUSED` to the server. The server gives the C4 to a random T each round (not in warmup), drops it where the carrier dies, G throws it 64 units ahead (`IN_DROP`, 1 s before pickup), Ts pick it up by walking over it. `mp_c4timer` 40 s; once planted the clock stops, all-Ts-dead no longer ends the round, all-CTs-dead does. Explosion: CS:GO gaussian (damage = radius, sigma = radius × 3.5 / 3, cut at radius × 3.5), through walls, as a chest hit (armor ratio 1). Money: bomb/defuse win $3500, planter and defuser +$300, Ts +$800 each if they planted and lost, Ts alive when time runs out get nothing. The snapshot carries the bomb state (+ position and ticks left once on the ground). Client: bomb model in `client/gl/players.js`, C4 viewmodel, `C4` HUD icon (blinks in a site), progress bar, round bar shows C4 instead of the clock, beeps faster and faster (interval approximation), explosion puff + sound (`client/audio.js`, WebAudio synthesis; starts on the first click). Offline has no bomb logic (planting just consumes the C4).
* **Not yet (Phase 7):** hostages, grenades, weapon drops/pickup (only the C4 so far), scopes/burst/silencer toggles, player models, most sounds, spectating.
* **Client presentation:** bullet decals (`client/gl/decals.js`, ring buffer), box-built viewmodels (`client/gl/viewmodel.js`), GPU crosshair (`client/gl/crosshair.js`), DOM HUD updated only on change (`client/weaponview.js`). Keys: 1/2/3/5 slots, Q last weapon, R reload, E use/defuse, G drop the C4, B buy, Tab scores, mouse wheel jump.
