# Project Overview: ComicStrike, a Procedural Web FPS

**Concept:** A lightweight, high-performance web-based multiplayer FPS. It combines the advanced mechanical logic and physics of CS:GO with the simplified geometry of classic CS 1.6 maps, rendered as a procedural comic print: flat colors, ink lines and halftone dots.

**Design Philosophy:** Built through first-principles engineering, the project utilizes a zero-dependency, self-contained architecture. The client executes directly in the browser via standard ES Modules—requiring no npm packages, bundlers, WebAssembly, or third-party graphics libraries. Every system is micro-optimized to eliminate garbage collection spikes, minimize input lag, and maximize frame rates.

## 1. Technical Stack

* **Language:** Vanilla JavaScript (ES6 Modules) and standard Web APIs.
* **Graphics:** Pure WebGL2 (Bare-metal rendering).
* **Networking:** WebTransport (HTTP/3 QUIC) for native UDP-like datagram transmission.
* **Map Format:** Direct GoldSrc BSP (Version 30) binary parsing.

## 2. Core Systems & Architecture

### Graphics & Rendering (The Comic Print)

* **Zero-Asset Pipeline:** The game loads exactly zero image or texture files.
* **Procedural Fragment Shaders:** The visual identity is a comic book: flat colors with sparse ink marks per surface class (some bricks outlined, plank seams, tile grout), shade printed as halftone dots, ink outlines on every silhouette, crease and part. Surface classes come from texture names (e.g., `metal`, `crate`) extracted from the map file; colors from the original textures' averages.
* **Single-Draw-Call Geometry:** Map geometry is packed into a single Vertex Buffer Object (VBO) to keep GPU draw calls as close to zero as possible (the opaque bulk in one draw with a shader that never discards, alpha-tested faces in a second: see Comic print, World).
* **One Print Pass:** everything draws into a G-buffer, then an ink pass at the G-buffer's resolution and one fullscreen composite shader print the frame (see Comic print).

### Map Parsing (GoldSrc BSP)

* **Native Binary Reading:** Native `fetch()` and `DataView` APIs are used to read CS 1.6 `.bsp` files directly into JavaScript `Float32Array` and `Int32Array` buffers.
* **Zero-Overhead Memory:** Because the parsed BSP lumps are already loaded into typed arrays, they are passed directly into WebGL2 buffers, bypassing the need for intermediate data structures or mesh conversions.

### Physics & Gameplay Logic (CS:GO Mechanics)

* **Modern Movement on Retro Geometry:** The engine implements CS:GO’s precise movement physics (acceleration, friction, air-strafing) mapped against the simplified collision hulls of CS 1.6 BSP architecture.
* **Strict Memory Management:** All game states, physics calculations, raycasting, and AABB collision sweeps are handled via pre-allocated `Float32Array` object pools to prevent JavaScript garbage collection from interrupting the main loop.

### Networking & Server Sync

* **WebTransport Datagrams:** Replaces WebSockets and WebRTC to provide a direct, low-latency connection without the overhead of STUN/TURN signaling servers.
* **Source-Style Netcode:** Utilizes fixed-tick server logic (e.g., 64-tick), client-side prediction, and server reconciliation, ensuring crisp hit registration that doesn't suffer from TCP head-of-line blocking.
* **Pragmatic Backend:** The server architecture remains lightweight enough to be deployed directly onto custom self-hosted Linux environments (such as DietPi setups or Pterodactyl panels) with minimal overhead.

* **Performance (Phase 11c):** hot paths (every frame, every tick) allocate as little as possible. Measured traps in V8: `Math.hypot` is a builtin call that allocates its result (hot client code uses `Math.sqrt` of the squares; shared simulation code keeps `hypot` for bit-exact results); typed-array `subarray` makes a view object (copy with index loops); floating-point arguments to a function that is not inlined are boxed on every call (the recursive hull trace passes its arguments through a preallocated per-depth stack, `ARGS` in `shared/trace.js`; the limb solver writes its math out); array or object literals, closures and template strings built every frame (hoisted, reused, or rebuilt only when their inputs change: the HUD's round bar and banner, the spectator notice, the radar font). Measure allocations with V8's sampling heap profiler from Node (`node:inspector` `HeapProfiler.startSampling` with `includeObjectsCollectedByMajorGC/MinorGC`; the server and client/anim modules run under Node as they are, with Math.random seeded for repeatable runs), and in the browser by summing heap rises (`performance.memory`) while stubbing subsystems. 5v5 numbers: server ~0.14 ms and ~17 KB per tick with 10 bots; client ~11 KB per frame with 9 animated players (was ~37). Measured again (a headless 10-bot de_dust2 game, 2000 ticks after a forced GC, 256 MB semispace): the whole server allocates ~1 KB a tick, the bot brain's small result objects included (V8 elides most of them), so nothing is left worth the code there; WebGL uniform calls remain.

Timing every pass (~15 queries a frame) itself slows a GPU near its limit: at 2560×1440 ×1.2 on the Iris Xe, 59 → 42 fps with `cl_showfps 3` on. So with it off one query covers the whole frame (`light`), always: the frame's GPU time (`frameMs`) and how many frames old its result is when it comes back (`behind`; 2 at ease in Chrome, the readback's own delay, 4 on an overloaded GPU, whose frames the browser queues: mouse lag before any frame is late), both eased, for r_dynres, `cl_showfps 2` (`gpu 9.3 ms, 2.0 frames behind`) and the benchmark. At 60 fps an integrated GPU idles between frames at low clocks, so every pass reads ~3× its real cost; `r_drawrepeat 20` (not saved) draws each frame 20 times back to back, keeping the GPU at full clock (also on a hidden page, whose rAF otherwise runs at ~1 fps), and the readout is then per drawing. Compare variants by ratios to a pass they cannot touch, averaged over many readings: absolute levels still drift ~3× between runs. Three measures:
    * **Automatic resolution** (`client/dynres.js` `DynamicResolution`, `r_dynres` 1, Video: Automatic resolution): with GPU timings (the light query above) it keeps the GPU ahead of the frame, judged over windows of 0.5 s: a step of 0.05 down once the GPU takes over 80 % of the frame (`DOWN_SHARE`, of 16.7 ms or a slower display's interval; double over all of it or with late frames) or, busy over half the frame, its results come back 0.8 frames later than the lowest ever seen (`BEHIND_RISE`, the floor in whole frames), before any frame is late; a step up only after 3 s clean when the next scale's GPU time, growing with its pixels, is predicted under 60 % of the frame (`UP_SHARE`), so it never tries a scale that brings late frames back (a GPU at low clocks reads slow, which only makes going up later); a step down soon after a step up doubles the wait. At 2560×1440 ×1.2 in the pane (Iris Xe): 41-59 fps, GPU 16-21 ms, 4 frames behind at a fixed scale; it settled at 0.85-0.9 with GPU ~9-10 ms and 2 frames behind (the floor), 59.2 fps, 1 % slow. Before (gaps only) it stepped down only after a stutter and probed up every 4 s into one, and never saw the queued frames. Where it settles (held 10 s) is kept per window size in localStorage (`comicstrike.dynres`, as a scale of the canvas), and the next map starts there instead of at full scale (a stutter at every map start). Without timings (some browsers) the old way, from the gaps between frames alone: windows of 0.5 s with over 8 % slow frames take the scene's render scale a tenth down, to half the canvas (`mat_viewportscale` sets the most), and once there the print's own resolution (the canvas, `print`: 0.85, then 0.7, stretched by the browser, for a GPU where the print itself is the cost: on the user's laptop the print was 40 % of the frame on de_cache); 4 s with no slow frames tries a step up (the print back first, then the scene by 0.05), and a try that brings slow frames back within 3 s steps back and doubles the wait (to 64 s); 1 s between steps, stalls over 250 ms ignored, 2 s of grace after a map load (both ways).     * **Cheaper G-buffer and print (Phase 13b):** three measures at the 5v5 view above, 1536×864, full clock (`r_drawrepeat 20`): 3.27 → 1.74 ms a frame (print 1.38 → 0.67, clear 0.62 → 0.01, world 0.74 → 0.63). (1) The depth target holds `DEPTH_NEAR` / depth as a half float (RG16F, flags in G): the print's dozen depth fetches read it as it is, where unpacking 24 bits from an RGBA8 (integer converts, shifts, a divide per neighbor) was a third of the print pass; the packed format stays as the `DEPTH_PACKED` fallback. (2) The color targets are not cleared: every pixel is written each frame (the world, else the sky fill at the far plane), and the three clears were a fifth of the frame. (3) The diagonal ink samples (4 depth fetches and a normal) are fetched only where the four direct neighbors already show something (a depth bulge over 1 %, a crease over 0.06, another id, other flags); on a plane inside one surface they add nothing. One change to the picture: along diagonal edges the line loses the staircase pixels only a diagonal sample saw (1 px on the far side), so diagonal lines are now as wide as axis-aligned ones instead of a pixel wider; axis-aligned lines are pixel-identical (checked with `readPixels` against the old code at a fixed sandbox view).

At best 21 % of the GPU frame (dropping the third target's write and clear), but the first-person view clears depth, and the print reads the flags of all 8 neighbors, which would then need the normal target too (16 fetches a pixel instead of 12). WebAssembly: the CPU is not the limit (2.7 ms of 16.7), so it would buy no frames, for a build step and a second copy of the bit-exact shared simulation.
* **File names vs ad blockers:** privacy filter lists block some script URLs by name (`hitbox.js` was blocked as an analytics tracker, freezing the client on load). Avoid names like `hitbox`, `analytics`, `track`, `ads`, `beacon`, `stats` in client-served files.
* **Layout:** `shared/` = code run identically by client and server (BSP parsing, physics, protocol); `client/` = browser only; `server/` = Deno only.
* **Lighting:** the BSP's own lighting lump is packed into one lightmap atlas texture at load time (map data, not an image file; at most `ATLAS_MAX_H` 8192 rows, faces past it lit by the grey block: a crafted map's faces can share one block of light while each asks for its own rectangle); albedo is fully procedural.
* **Textures (Phase 8b):** surfaces stay flat and simple: the name class patterns of `shared/materials.js` (cheap, flat, few colors), colored like the originals. `tools/gen_texturedata.js` measures every miptex in `wads/` and every texture embedded in `maps/*.bsp` (`tools/wad.js`, `tools/texanalysis.js`, one worker per core, a few seconds) and writes `client/texturedata.js`: per texture name, the main surface's average color (color bands such as a wainscot or trim strip and transparent texels left out) and whether the original repeats in lines. That is 4 bytes each for about 5,800 textures, ~90 KB, no pixels. `client/texcolors.js` `withOriginalColor` applies it in `client/mapmesh.js`: the original color replaces the name-guessed one, and brick/tile patterns become plain where the original has no repeating lines (brown plaster named like brick). Unknown names keep the name classes. Rerun the tool after adding WADs or maps with embedded textures. A richer fitted model (noise spectra, grids, bands) was tried and dropped as too heavy and too busy for the art style.
* **Chrome datagram limit:** `maxDatagramSize` is 1024 bytes — every packet must fit.
* **Movement (`shared/pmove.js`):** Source `FullWalkMove` ordering with CS:GO convars (`MOVE` table). Player origin is the GoldSrc hull *center* (standing hull 32×32×72, duck hull 32×32×36 — fixed by the BSP clipnodes), so eye heights are 64 standing / 30 crouched above the feet. Crouch-jump raises feet 9 units like CS:GO. A jump never carries more than 1.1 × the max speed (`sv_enablebunnyhopping 0`, PreventBunnyJumping), so strafe-jumping cannot keep building speed. Standing up takes the standing hull as soon as there is room and the view rises with the duck amount (the eye cannot rise above a ducked hull, so keeping that hull until the amount reached 0 held the view down, then popped it up 30 units). Stamina constants are CS:GO's (`sv_staminajumpcost` 0.08, `sv_staminalandcost` 0.05, max 80, recovery 60); the speed formula is an approximation, tuned by feel. `docs/csgo-parity.md` (Phase 14c) lists every rule checked against CS:GO, what was fixed and what stays different. Standing on another player (CS:GO's boosts, Phase 14d): the ground entity is his body and his velocity is our base velocity, the conveyor path (`checkMovingGround`; Source's SetGroundEntity adds the ground's velocity on leaving it): we ride a running teammate, and jumping off him (or his stopping under us) folds his speed into ours on top of our own, past the jump's 1.1 × cap: the run boost (~280 u/s off a teammate running at 250, then air strafing). A crouching player standing up lifts whoever stands on him (`liftOffBodies`: feet in a body's upper half go onto its top; the ducked hull is 36 tall, so a crouch boost is 36 here, 54 in CS:GO); a player on our head blocks our jump. `test/pmove.test.js` players tests.
* **Collision (`shared/trace.js`):** hull 0 is rebuilt from BSP nodes and appended after the clipnodes; one recursive trace serves all hulls. Solid brush entities are `func_*` minus a non-solid list; `func_ladder`/`func_water` are volumes. Entities can move and turn (`setTransform`, doors): a turned one is traced in its model space like GoldSrc's SV_ClipMoveToEntity (the hull box itself is not turned), with sphere bounds; `toLocal` maps a world point into it (surface lookups). Players are solid to each other's movement (Phase 14d): the living players are packed every tick as bodies (`setBody`, by player id, so a client's prediction and the server agree on the ground entity's index: half height 36, 18 ducked, velocity, team), and the player hull trace (`tracePlayer`, pmove's alone: bullets never see them, the hit groups do players) clips against each body's box grown by the hull, a box the trace starts inside passed through (two players left overlapping walk out of each other). `mp_solid_teammates` (1; casual 0, approx.; `GAME_GHOST_TEAM` in the round block tells the clients) lets teammates pass through, enemies always block. The server runs each command against the others where they are now (CS:GO: no lag compensation for movement); the client predicts against the newest snapshot's positions, moving at the speed between the two newest snapshots, so a touched player who moved brings a correction (CS:GO jitters the same way on a moving teammate).
* **Weapons (`shared/weapons.js`):** CS:GO accuracy model (penalty + recovery with the start/end-bullet transition, movement/air inaccuracy, jump/land penalties; `EV_APEX` from pmove at the top of a jump adds `inaccuracy jump apex`, the Desert Eagle's second jump penalty), spread seeded by the tick/command number, aim punch with CS:GO recoil convars. Fire rates are tick-quantized (AK: 7 ticks/shot at 64 tick), as in CS:GO. An empty magazine reloads by itself once the last shot's cycle is over, trigger held or not (with no reserve the trigger dry-fires); round survivors' guns come back loaded with a full reserve (`refillAmmo` in `spawnPlayer`).

Never hand-edit it; HUD labels, reload times (until the gun fires again) and deploy times (not in that file: they live in the model animations) are in `EXTRA` in weapons.js, taken from the community CS:GO weapon spreadsheet's measurements (deploy 1.0 s for most guns, 1.83 for the CZ75, 1.25 for the AWP). The March 2026 CS2 spreadsheet was compared too: the only differences from our data are CS2's balance changes (SMG damage and prices, FAMAS accuracy, kill awards), kept out on purpose.

The formula was confirmed by matching documented spray shapes (AK, Galil, FAMAS, SG 553, MAC-10); tests pin them.

  * **Phase 14i, the leftovers:** the Negev's tightening needs no code of its own: CS:GO's data gives it a recovery time of 0.3 s falling to 0.1 s over bullets 9-12, so its spray fires at ~51 mrad through shot 10 and holds at ~19 from shot 14 on (the AK's steady spray ~19 too: the Negev's is a rifle's spray that starts wild), with a recoil angle of 0 and no variance (straight up); `test/weapons.test.js` pins it. Shotguns fire a fixed pellet pattern: in `fire()` the spread offsets of a gun with a `spread seed` (the four shotguns) come from a `UniformRandomStream` seeded with it at every shot (angle first, then the radius; CS:GO's `weapon_accuracy_shotgun_spread_patterns`), so the pattern is the same shot after shot and only the per-pellet inaccuracy still scatters it; the stream is shared code, so the prediction stays exact. The camera's own jolt (`weapon_recoil_view_punch_extra` 0.055, `view_punch_decay` 18): each predicted `WEV_FIRE` adds that share of the shot's recoil kick (`shotKick`: the recoil table entry the shot used) to `viewKick` in main, decayed every frame and added to the camera's pitch and yaw beside the aim punch's 45 %; it lives in no weapon state, so the bullets and the server never see it (CS:GO's is a view punch too). Both the decay's shape and the kick's yaw share are approximations.
* **Breakables (`shared/breakables.js`):** `func_breakable` with GoldSrc semantics: `health`, `material` (missing = glass), spawnflag 1 trigger-only (CS bomb-site crates: bullets do nothing), 256 one-hit melee, material 7 unbreakable. Bullets deal CS:GO damage with range falloff (`damageAtRange`). Each breakable has a slot (1..255, BSP entity order) stored in vertex byte 39; the world vertex shader drops triangles of broken slots via the `u_broken` bitmask, so the world stays one draw call. Broken ones become `ENT_NONE` (no collision), lose their decals and burst into instanced procedural debris (`client/gl/debris.js`). They reset on respawn (round restart). Mapper-built crates are often several overlapping breakables (fy_buzzkill: lid/shell, hollow walls, floor slab) that break separately, as in GoldSrc. Bullets that do not break one go on through it by its material like any wall (Phase 7a's penetration). Phase 14h: a break fires the breakable's `target` after its `delay` and its `killtarget` (CBreakable::Die; `Game.brokeSlot`, for a bullet's break, a blast's or a name's), and one with `explodemagnitude` explodes: that much damage at its center falling off in a straight line to nothing at 2.5 times it (`EXPLODE_RANGE`, HL RadiusDamage), blocked by walls, on every player (as a chest hit, `BLAST`, the shooter credited) and breakable in reach (`Breakables.blast`: trigger-only ones left alone), so crates chain; the clients see it as `FX_BLAST` (the magnitude in the weapon byte) and print a comic explosion sized by it. * **Netcode (Phases 5-6):** `shared/protocol.js` is the binary wire format (v19; preallocated `Writer`/`Reader`, every message ≤ `MAX_DATAGRAM` 1024). Client → server: `HELLO` (resent every 250 ms until `WELCOME`; v14: it names the room, see Your own maps and rooms), then `CMDS` every tick with the newest 4 user commands (redundancy) plus the snapshot ack; each command carries `viewTick`, the server tick the player was seeing others at. An empty `CMDS` is the 1 Hz keepalive; `BYE` on page hide frees the player at once (Deno does not surface the browser's session close). A session that never opens (timed out after 3 s, handshake refused) fails `NetClient.connect` with its reason, which the start menu shows ("Could not start: ..."); the client is then closed, and `close()` / `send()` pass over a client with no session (before, the goodbye went to the missing writer and threw, so the menu hung on Connecting and the reason was lost; `test/net.test.js`). Server (`server/game.js`, drift-free 64 Hz loop in `server/main.js`) runs commands through `shared/player.js` (the same code the client predicts with), one per tick plus an 8-command bank, repeating the last one when lost beyond redundancy. Snapshots every tick: own state in full (raw `PlayerState` bytes; the `WeaponState` as a bitmask of its non-zero fields and those f64 values, bit-exact and far smaller), other players delta-compressed against the client's last ack (`SnapshotRing`, 32 deep), the breakable mask, the doors' states (v11, see Doors), then the tick's events (world impacts except the receiver's own, blood hits, and kills repeated for `KILL_REPEAT_TICKS`). `INFO` (names/teams) every second and on roster changes.
  * **Prediction/reconciliation (client/main.js):** the client stores its state after every command; each snapshot's own state is compared byte-for-byte with the prediction for `lastCmd`; on mismatch it adopts the server state, replays later commands and blends the visible correction away (`smooth`, 15/s). Respawns are adopted the same way. Must stay bit-exact: `test/server.test.js` checks it through the wire with packet loss; the HUD shows the live exact rate.
  * **Interpolation:** other players render `INTERP_TICKS` (2 = CS:GO `cl_interp_ratio 2`) behind a smoothed server clock, lerped between the two bracketing snapshots. They are drawn as animated models (Phase 8d).
  * **Hits and lag compensation (`shared/hitgroups.js`):** four CS:GO hit groups (head ×weapon headshot multiplier, chest 1, stomach 1.25, legs 0.75) as yaw-rotated boxes that squash when crouching. The server keeps 64 ticks of position history and rewinds every target to the shooter's `viewTick` before tracing (`sv_maxunlag` 1 s; `Game.viewOf`: the tick unwrapped, since it crosses the wire as ticks × 256 in 32 bits and wrapped after 72.8 hours on one map, every shot then rewinding a second; and no more than `VIEW_SLACK` 13 ticks, CS:GO's 200 ms, behind the shooter's newest acked snapshot less the interpolation, so a modified client cannot claim a second ago); the nearer of world and player wins. Damage is truncated like CS:GO; friendly fire is off; the dead respawn after 2 s. The client stops its own bullets at the players it sees but shows hits only when the server's blood events arrive. Hidden tabs keep applying snapshots/events from a timer, and take the console lines and chat as they come, their pings dropped (on return, minutes of them showed as new and every ping played at once).

* **Models (Phase 8c, toolkit for 8d-8f):** low-poly, flat, few colors (see the art style above), built in code at load.
  * `client/gl/meshkit.js` `MeshBuilder`: box, rbox (every edge rounded: a grid on the faces pushed onto the rounded surface), sphere, slab (rounded vertical edges), lathe (about z), capsule, extrude (side outline along y), loft (z sections) under a transform stack (translate / rotate with GoldSrc angles / scale), `warp(fn)` (moves each corner by position before its normal is taken: a lumpy cloud out of a sphere) and `mirror` (flips winding, swaps bones through `Skeleton.mirror`); `bevel(r)` rounds the next boxes (a chamfer) and extrusions (45° cut, the outline inset on the faces). Every primitive is closed and wound counter-clockwise from outside. Normals are smooth within a primitive across edges flatter than its crease angle (`smooth(deg)`, 50° by default, 0 = faceted; weighted by corner angle × area), so round parts shade round and the composite inks no crease on them, while box corners stay sharp; separate primitives never blend. The flat faces of bevelled boxes and outlines are hard: they keep their own normal, and the bevels bend from one face's normal to the next (rounded edges on flat sides that still print flat, which the shine needs). `sweep(sections, seg, up, ends)` sweeps a tube along a path of oval or rounded-box sections (superellipse exponent `n`) square to the path, with round or flat ends: torsos and limbs in one piece. `skin(fn)` skins the next vertices by position: fn returns two bones and the second's weight (mirrored halves remap both), so a limb tube blends across its joints. Vertices are 24 bytes: position, normal, the heavier bone, color + finish (`FINISH`: cloth, skin, metal, polymer, wood, pattern, and the gun looks' camo, stripes, hex, fade; `finish(rgb, f)` makes a color that carries one, `defaultFinish` for the rest), the second bone and its weight, a pattern coordinate (the fade's place along a gun; read with the bones as one 4-byte attribute).
