# Project Overview: ComicStrike, a Procedural Web FPS

**Concept:** A lightweight, high-performance web-based multiplayer FPS. It combines the advanced mechanical logic and physics of CS:GO with the simplified geometry of classic CS 1.6 maps, rendered as a procedural comic print: flat colors, ink lines and halftone dots.

**Design Philosophy:** Built through first-principles engineering, the project utilizes a zero-dependency, self-contained architecture. The client executes directly in the browser via standard ES Modules—requiring no npm packages, bundlers, WebAssembly, or third-party graphics libraries. Every system is micro-optimized to eliminate garbage collection spikes, minimize input lag, and maximize frame rates.

## 1. Technical Stack

* **Language:** Vanilla JavaScript (ES6 Modules) and standard Web APIs.
* **Graphics:** Pure WebGL2 (Bare-metal rendering).
* **Networking:** WebTransport (HTTP/3 QUIC) for native UDP-like datagram transmission.
* **Map Format:** Direct GoldSrc BSP (Version 30) binary parsing.

## 2. Core Systems & Architecture

### Graphics & Rendering (The Comic Print)

* **Zero-Asset Pipeline:** The game loads exactly zero image or texture files.
* **Procedural Fragment Shaders:** The visual identity is a comic book: flat colors with sparse ink marks per surface class (some bricks outlined, plank seams, tile grout), shade printed as halftone dots, ink outlines on every silhouette, crease and part. Surface classes come from texture names (e.g., `metal`, `crate`) extracted from the map file; colors from the original textures' averages.
* **Single-Draw-Call Geometry:** Map geometry is packed into a single Vertex Buffer Object (VBO) to keep GPU draw calls as close to zero as possible (the opaque bulk in one draw with a shader that never discards, alpha-tested faces in a second: see Comic print, World).
* **One Print Pass:** everything draws into a G-buffer, then one fullscreen composite shader prints the frame (see Comic print).

### Map Parsing (GoldSrc BSP)

* **Native Binary Reading:** Native `fetch()` and `DataView` APIs are used to read CS 1.6 `.bsp` files directly into JavaScript `Float32Array` and `Int32Array` buffers.
* **Zero-Overhead Memory:** Because the parsed BSP lumps are already loaded into typed arrays, they are passed directly into WebGL2 buffers, bypassing the need for intermediate data structures or mesh conversions.

### Physics & Gameplay Logic (CS:GO Mechanics)

* **Modern Movement on Retro Geometry:** The engine implements CS:GO’s precise movement physics (acceleration, friction, air-strafing) mapped against the simplified collision hulls of CS 1.6 BSP architecture.
* **Strict Memory Management:** All game states, physics calculations, raycasting, and AABB collision sweeps are handled via pre-allocated `Float32Array` object pools to prevent JavaScript garbage collection from interrupting the main loop.

### Networking & Server Sync

* **WebTransport Datagrams:** Replaces WebSockets and WebRTC to provide a direct, low-latency connection without the overhead of STUN/TURN signaling servers.
* **Source-Style Netcode:** Utilizes fixed-tick server logic (e.g., 64-tick), client-side prediction, and server reconciliation, ensuring crisp hit registration that doesn't suffer from TCP head-of-line blocking.
* **Pragmatic Backend:** The server architecture remains lightweight enough to be deployed directly onto custom self-hosted Linux environments (such as DietPi setups or Pterodactyl panels) with minimal overhead.
## Development

* **Runtime:** Deno (≥ 2.9) for the server, static file serving and tests. The WebTransport server uses Deno's unstable QUIC API (`Deno.QuicEndpoint` + `Deno.upgradeWebTransport`), isolated in `server/transport.js`. No npm/jsr packages anywhere.
* **Run:** `deno task start` (env `MAP=de_dust2`), then open `http://127.0.0.1:27015/`: the start menu (see Start menu). URL parameters skip it for testing: `?team=t|ct|spec&name=…&primary=ak47&secondary=deagle` joins at once (the sandbox if no server answers); `?practice&map=…&mode=deathmatch&players=10&difficulty=2` starts a practice game (see Practice); `?offline&map=…` opens the sandbox (the player alone in the page, no game rules; noclip, `comicstrike.give`). Each browser tab is one player. TCP 27015 serves HTTP; UDP 27015 carries WebTransport. Clients connect via `127.0.0.1` (not `localhost`) because Chrome tries `::1` first.
* **Test:** `deno task test` (`Deno.test` + `node:assert`; map-dependent tests skip if `maps/*.bsp` is missing). `deno lint` must stay clean.
* **Certificates:** in development `server/cert.js` auto-generates a 13-day ECDSA P-256 self-signed cert in `certs/` with `openssl`; clients pin it via `serverCertificateHashes` fetched from `/connect.json` (browsers pin only certificates valid for at most 14 days). With `TLS_CERT` / `TLS_KEY` (a real certificate, e.g. Let's Encrypt) the pages go over HTTPS on `HTTP_PORT`, WebTransport uses the same certificate, `/connect.json` sends `certHash: null` and the client connects without pinning; `REDIRECT_PORT` (80) redirects plain HTTP to the site.
* **Deployment (`deploy/`):** `README.md` (DNS, firewall incl. UDP 443, Deno, copying code and maps, certbot standalone with stop/start hooks for renewals), `comicstrike.service` (systemd: the certificate handed over with `LoadCredential`, ports 80/443 via `CAP_NET_BIND_SERVICE`, read-only system, `DENO_DIR` in its cache directory), `comicstrike.env.example` (HTTP_PORT and GAME_PORT 443, REDIRECT_PORT 80, HOSTNAMES, MAP, RCON_PASSWORD). `deno task serve` runs the server without the self-signed certificate's write and openssl permissions.
* **Serving files and staying up:** the HTTP server serves only `client/`, `shared/`, `maps/` and the listed server files, by `server/static.js` `staticPath`: plain names (`[\w./-]`) and no dot segments, checked on the decoded path (Deno decodes a file URL's `%2F` into a separator: `/client/gl%2F%2E%2E%2F%2E%2E%2Fcerts%2Fkey.pem` passed the old check of the raw path and served the TLS key; `test/static.test.js`). A tick that throws is logged at most once a second and the game goes on (`Host.step`, used by the server and the practice worker; uncaught, it ended the Deno process and froze practice); the client asks for its next frame before drawing this one, so a frame that throws costs one frame.
* **Maps:** `maps/` holds Valve CS 1.6 BSPs — copyrighted, git-ignored, never commit them. The one exception is our own `maps/de_playground.bsp` (see Test map), tracked through a `.gitignore` exception.
* **Test map (`tools/gen_demomap.js` → `maps/de_playground.bsp`, `deno run --allow-write=maps tools/gen_demomap.js`, ~2 s, deterministic):** the demo's playground, a walled courtyard under the sky with every element to try: stairs to a platform, a 320-unit ladder tower, breakable wooden / metal crates and a glass pane and an unbreakable crate, a conveyor belt (`func_conveyor`, east at 160; its top `scroll_conv` slides east), a metal yard and shed, a pool (shallow 14 at one end, knee-deep 30 at the other: splash and wade footsteps), a sliding door, a swinging door, a garage door a button opens, a free-standing wall, bomb sites A and B with crates, both spawns with buy zones. A small compiler of our own writes it as a real BSP 30 file from axis-aligned boxes only (box helpers: per-side textures, `null` for no face): per model and hull a k-d tree on the boxes' faces (hulls 1-3 use the boxes grown by the player hulls, exact for boxes); faces are the sides of empty cells touching solid ones, each hung on the node whose plane it lies on (the light point lookup needs that), merged back into rectangles, wound clockwise from the front; a rotating door's model is relative to its `origin` key; lightmaps (16 units a texel) are baked there: a warm sun with shadows plus a cool sky seen through 18 rays, traced against the boxes (open ground ~228, under the clamp). Only the lumps the engine reads are filled (no visibility, no marksurfaces). `test/playground.test.js`: every element present, spawns on the floor, walls and sky hold, pool depths, the ladder climbs onto the tower, the belt carries, doors and breakables load, sun and shade, bot paths to both spawns, sites, the tower top and the platform.
* **WADs:** `wads/` holds CS 1.6 texture WADs — copyrighted, git-ignored, never commit them. They are only for studying the original textures to tune the procedural ones (textures stay procedural at runtime).
* **Performance (Phase 11c):** hot paths (every frame, every tick) allocate as little as possible. Measured traps in V8: `Math.hypot` is a builtin call that allocates its result (hot client code uses `Math.sqrt` of the squares; shared simulation code keeps `hypot` for bit-exact results); typed-array `subarray` makes a view object (copy with index loops); floating-point arguments to a function that is not inlined are boxed on every call (the recursive hull trace passes its arguments through a preallocated per-depth stack, `ARGS` in `shared/trace.js`; the limb solver writes its math out); array or object literals, closures and template strings built every frame (hoisted, reused, or rebuilt only when their inputs change: the HUD's round bar and banner, the spectator notice, the radar font). Measure allocations with V8's sampling heap profiler from Node (`node:inspector` `HeapProfiler.startSampling` with `includeObjectsCollectedByMajorGC/MinorGC`; the server and client/anim modules run under Node as they are, with Math.random seeded for repeatable runs), and in the browser by summing heap rises (`performance.memory`) while stubbing subsystems. 5v5 numbers: server ~0.14 ms and ~17 KB per tick with 10 bots; client ~11 KB per frame with 9 animated players (was ~37). Left: the bot brain's per-tick result objects and arrays (~3 KB/tick), WebGL uniform calls.
  * **GPU time** (`client/gl/gputimer.js`, `cl_showfps 3`; Settings, Video: Frame rate): per pass (clear, world, sky, models, effects, glass, view, print, over) from `EXT_disjoint_timer_query_webgl2` queries averaged over 250 ms (where Chrome hides it, `gl.finish` timing: coarse, and it slows the frame), plus the CPU time of the ticks and of building the frame. At 60 fps an integrated GPU idles between frames at low clocks, so every pass reads ~3× its real cost; `r_drawrepeat 20` (not saved) draws each frame 20 times back to back, keeping the GPU at full clock (also on a hidden page, whose rAF otherwise runs at ~1 fps), and the readout is then per drawing. Compare variants by ratios to a pass they cannot touch, averaged over many readings: absolute levels still drift ~3× between runs. Never judge a saving at 60 fps: the GPU clocks down to fill the frame, so the other passes stretch by what was taken out (dropping the color clears read as nothing at 60 fps and was a fifth of the frame at `r_drawrepeat 20`). A fixed view: `?practice&map=de_dust2&players=10&team=ct`, `rcon mp_freezetime 60; rcon sv_cheats 1; rcon mp_restartgame 1`, then `setpos 448 2464 -128; setang 0 255` (CT spawn, teammates in view). There at 1280×720 on an Intel Iris Xe, 60 fps: ~8.4 ms (was ~10.6: world 2.9 → 2.3 without a discard in the opaque shader, models 2.4 → 1.3 indexed and culled; looking away from the players models fall to ~0.2); at full clock the whole frame is ~2.8 ms: print ~0.9 (its base ~0.3, the ink ~0.5, the dots almost nothing), world ~0.7, clear ~0.4, models ~0.3. Tried and dropped, within noise: a depth pre-pass for the world (it costs what it saves now that the opaque shader has no discard); `invalidateFramebuffer` on the color targets (nothing on D3D11). Animating the players is ~0.15 ms of CPU a frame, so off-screen players are still posed (no stale pose when they come into view); the limb solver's target and pole go through `Pose.goal` (`reachGoal`), not six boxed arguments (9 animated players: ~2.9 → ~0.6 KB a frame). The canvas size comes from a ResizeObserver (reading `clientWidth` every frame forced a layout after any DOM write in the ticks).
  * **Weak GPUs (Phase 13):** the goal is 60 fps on anything with a browser. On the Iris Xe laptop on battery, a 5v5 practice on de_dust2 at 1536×864 ran 46-49 fps with a quarter of the frames missing vsync, and the GPU was the limit (CPU ~2.7 ms a frame; 75 % resolution gave 58.7 fps, 50 % or `r_comic 0` a locked 60). `benchmark [seconds]` (console, in a game) prints the frame rate, the share of slow frames (over 21 ms), frame-time percentiles, CPU per frame and GPU per pass for the fixed view above. Three measures:
    * **Automatic resolution** (`client/dynres.js` `DynamicResolution`, `r_dynres` 1, Video: Automatic resolution): from the gaps between frames alone (timer queries are missing in some browsers), windows of 0.5 s with over 8 % slow frames take a step down, first the fast ink, then the render scale a tenth at a time down to half the page's pixels (`mat_viewportscale` and `r_hidpi` set the most); 4 s with no slow frames tries a step up (0.05, then the full ink), and a try that brings slow frames back within 3 s steps back and doubles the wait (to 64 s); 1 s between steps, stalls over 250 ms ignored, 2 s of grace after a map load. Resizing the canvas and G-buffer costs no visible hitch. With the GPU work doubled (`r_drawrepeat 2`, a weaker GPU): 38.5 fps / 53 % slow without, 59.0 fps / 2 % slow with (settled at 65 % and fast ink). `cl_showfps 2` shows the resolution.
    * **Visible world only, nearest first** (`client/gl/worldvis.js` `WorldVis`, GoldSrc's R_MarkLeaves / R_RecursiveWorldNode): on entering a leaf its PVS row marks the visible leaves and their parents; every frame the BSP is walked near child first, skipping unmarked nodes and boxes outside the frustum's side planes, and the world's opaque faces in the leaves reached are copied (`buildMapMesh`'s `faceFirst` / `faceCount`) into one of two spare regions at the end of the index buffer (taken in turns), so the GPU rejects hidden pixels before shading. 5-7 % of a map's triangles drawn, ~0.03 ms of CPU, the world pass 12-27 % cheaper on de_dust2 (picture identical); brush entities, sky, alpha-tested and see-through faces as before; no visibility lump (de_playground) or a camera in solid draws everything; `r_novis 1` too, for comparisons.
    * **Fast ink** (`r_inkfast`, Video: Ink lines; `COMPOSITE_FAST_FS` defines `INK_FAST`): the ink from the four direct neighbors only (no diagonal depth fetches, no diagonal crease), looking the same. It was a third of the print pass; since Phase 13b the full print fetches the diagonals only near edges and costs the same, so the setting (and r_dynres's first step) buys nothing measurable now.
    * **Mouse latency:** the mouse deltas are applied at the start of the frame and the view uses the angles as they are, so what is left is the browser's display pipeline: the frame drawn in a `requestAnimationFrame` goes to the compositor at the next vsync and to the screen at the one after. `r_lowlatency` (Video: Low-latency display, on by default, read when the context is created, so it takes a reload) asks for a `desynchronized` canvas: where the browser honors it (Chrome on Windows) the frame skips the compositor, a frame less of lag, at the risk of a tear during fast turns (none seen; only the print writes the canvas now; when every pass did, half-drawn frames flickered, which is why it was off). Dead ends: `gl.finish()` returns at once in Chrome (it does not wait for the GPU), so an end-of-frame wait to keep the GPU from running ahead does nothing; a fence's `SYNC_STATUS` turns signaled a task late, so it cannot measure how far the GPU runs behind.
    * **Cheaper G-buffer and print (Phase 13b):** three measures at the 5v5 view above, 1536×864, full clock (`r_drawrepeat 20`): 3.27 → 1.74 ms a frame (print 1.38 → 0.67, clear 0.62 → 0.01, world 0.74 → 0.63). (1) The depth target holds `DEPTH_NEAR` / depth as a half float (RG16F, flags in G): the print's dozen depth fetches read it as it is, where unpacking 24 bits from an RGBA8 (integer converts, shifts, a divide per neighbor) was a third of the print pass; the packed format stays as the `DEPTH_PACKED` fallback. (2) The color targets are not cleared: every pixel is written each frame (the world, else the sky fill at the far plane), and the three clears were a fifth of the frame. (3) The diagonal ink samples (4 depth fetches and a normal) are fetched only where the four direct neighbors already show something (a depth bulge over 1 %, a crease over 0.06, another id, other flags); on a plane inside one surface they add nothing. One change to the picture: along diagonal edges the line loses the staircase pixels only a diagonal sample saw (1 px on the far side), so diagonal lines are now as wide as axis-aligned ones instead of a pixel wider; axis-aligned lines are pixel-identical (checked with `readPixels` against the old code at a fixed sandbox view).
    * Tried and dropped: a two-target G-buffer (depth read back from the depth buffer). At best 21 % of the GPU frame (dropping the third target's write and clear), but the first-person view clears depth, and the print reads the flags of all 8 neighbors, which would then need the normal target too (16 fetches a pixel instead of 12). WebAssembly: the CPU is not the limit (2.7 ms of 16.7), so it would buy no frames, for a build step and a second copy of the bit-exact shared simulation.
* **File names vs ad blockers:** privacy filter lists block some script URLs by name (`hitbox.js` was blocked as an analytics tracker, freezing the client on load). Avoid names like `hitbox`, `analytics`, `track`, `ads`, `beacon`, `stats` in client-served files.
* **Layout:** `shared/` = code run identically by client and server (BSP parsing, physics, protocol); `client/` = browser only; `server/` = Deno only.
* **Lighting:** the BSP's own lighting lump is packed into one lightmap atlas texture at load time (map data, not an image file); albedo is fully procedural.
* **Textures (Phase 8b):** surfaces stay flat and simple: the name class patterns of `shared/materials.js` (cheap, flat, few colors), colored like the originals. `tools/gen_texturedata.js` measures every miptex in `wads/` and every texture embedded in `maps/*.bsp` (`tools/wad.js`, `tools/texanalysis.js`, one worker per core, a few seconds) and writes `client/texturedata.js`: per texture name, the main surface's average color (color bands such as a wainscot or trim strip and transparent texels left out) and whether the original repeats in lines. That is 4 bytes each for about 5,800 textures, ~90 KB, no pixels. `client/texcolors.js` `withOriginalColor` applies it in `client/mapmesh.js`: the original color replaces the name-guessed one, and brick/tile patterns become plain where the original has no repeating lines (brown plaster named like brick). Unknown names keep the name classes. Rerun the tool after adding WADs or maps with embedded textures. A richer fitted model (noise spectra, grids, bands) was tried and dropped as too heavy and too busy for the art style.
* **Chrome datagram limit:** `maxDatagramSize` is 1024 bytes — every packet must fit.
* **Movement (`shared/pmove.js`):** Source `FullWalkMove` ordering with CS:GO convars (`MOVE` table). Player origin is the GoldSrc hull *center* (standing hull 32×32×72, duck hull 32×32×36 — fixed by the BSP clipnodes), so eye heights are 64 standing / 30 crouched above the feet. Crouch-jump raises feet 9 units like CS:GO. Standing up takes the standing hull as soon as there is room and the view rises with the duck amount (the eye cannot rise above a ducked hull, so keeping that hull until the amount reached 0 held the view down, then popped it up 30 units). Stamina constants are approximations, tuned by feel.
* **Collision (`shared/trace.js`):** hull 0 is rebuilt from BSP nodes and appended after the clipnodes; one recursive trace serves all hulls. Solid brush entities are `func_*` minus a non-solid list; `func_ladder`/`func_water` are volumes. Entities can move and turn (`setTransform`, doors): a turned one is traced in its model space like GoldSrc's SV_ClipMoveToEntity (the hull box itself is not turned), with sphere bounds; `toLocal` maps a world point into it (surface lookups).
* **Weapons (`shared/weapons.js`):** CS:GO accuracy model (penalty + recovery with the start/end-bullet transition, movement/air inaccuracy, jump/land penalties), spread seeded by the tick/command number, aim punch with CS:GO recoil convars. Fire rates are tick-quantized (AK: 7 ticks/shot at 64 tick), as in CS:GO. An empty magazine reloads by itself once the last shot's cycle is over, trigger held or not (with no reserve the trigger dry-fires); round survivors' guns come back loaded with a full reserve (`refillAmmo` in `spawnPlayer`).
  * **Real game data:** `shared/weapondata.js` is generated by `tools/gen_weapondata.js` from CS:GO's final `items_game.txt` (all 34 guns, primary + alt modes). Never hand-edit it; reload times and HUD labels (not in that file) live in `EXTRA` in weapons.js and are approximate.
  * **Spray patterns:** generated exactly like CS:GO: Valve's `CUniformRandomStream` (bit-exact port) seeded with each gun's `recoil seed`, angle drawn before magnitude, full-auto tables lerp by `weapon_recoil_variance` 0.55, first 4 shots suppressed from 0.75. The formula was confirmed by matching documented spray shapes (AK, Galil, FAMAS, SG 553, MAC-10); tests pin them.
  * **Shotguns** (Nova, XM1014, Sawed-Off) load shell by shell like CS:GO: `SHELL_RELOAD` gives the delay before the first shell and the time per shell (approximations); `WS_RELOAD_END` is then the next shell's time, each shell raises `WEV_SHELL`, and pulling the trigger with a shell in stops loading. The MAG-7 uses its magazine.
  * **Modes (Phase 7d):** each gun carries both stat sets from the game data (`modes[0]` normal, `modes[1]` CS:GO's "Alt": scoped, burst, silencer on, the revolver's fan); `modeOf` / `weaponStats` pick the current one for spread, inaccuracy, recoil table and move speed (scoped AWP walks at 100). Right click: scopes cycle `zoomLevels` (CS:GO fovs per level, `zoom_sensitivity_ratio_mouse`; bolt-actions leave the scope for the bolt and come back, `WS_RESUME_ZOOM`; reloading unscopes; a quick scope is still inaccurate until the penalty recovers); the Glock and FAMAS toggle three-round bursts (`burstGap` between shots, `burstCycle` after); the USP-S and M4A1-S take the silencer off / put it on over `SILENCER_TIME` (approx.); the R8 fans on right click and fires primary `REVOLVER_COCK` after the trigger (approx.). Mode state lives after the slots: `WS_ALT` (bit per slot: silencer / burst), `WS_ZOOM`, `WS_MODE_END`, `WS_BURST_*`, `WS_COCK`. Client: scope overlay (`#scope`: black around a circle, cross lines, red dot for the AUG / SG 553) instead of the viewmodel and crosshair, no crosshair on unscoped snipers, the model without its silencer (`GunMeshes.meshOf`, third person via `ANIM_SILENCED`), the HUD label says the mode.
  * **Not yet modeled:** Negev's spread tightening, fixed shotgun spread patterns, the camera-only view punch (`weapon_recoil_view_punch_extra`).
* **Breakables (`shared/breakables.js`):** `func_breakable` with GoldSrc semantics: `health`, `material` (missing = glass), spawnflag 1 trigger-only (CS bomb-site crates: bullets do nothing), 256 one-hit melee, material 7 unbreakable. Bullets deal CS:GO damage with range falloff (`damageAtRange`). Each breakable has a slot (1..255, BSP entity order) stored in vertex byte 39; the world vertex shader drops triangles of broken slots via the `u_broken` bitmask, so the world stays one draw call. Broken ones become `ENT_NONE` (no collision), lose their decals and burst into instanced procedural debris (`client/gl/debris.js`). They reset on respawn (round restart). Mapper-built crates are often several overlapping breakables (fy_buzzkill: lid/shell, hollow walls, floor slab) that break separately, as in GoldSrc. Not yet: explosions (`explodemagnitude`), firing `target`, touch/pressure flags, spawned items, bullet penetration.
* **Netcode (Phases 5-6):** `shared/protocol.js` is the binary wire format (v13; preallocated `Writer`/`Reader`, every message ≤ `MAX_DATAGRAM` 1024). Client → server: `HELLO` (resent every 250 ms until `WELCOME`), then `CMDS` every tick with the newest 4 user commands (redundancy) plus the snapshot ack; each command carries `viewTick`, the server tick the player was seeing others at. An empty `CMDS` is the 1 Hz keepalive; `BYE` on page hide frees the player at once (Deno does not surface the browser's session close). Server (`server/game.js`, drift-free 64 Hz loop in `server/main.js`) runs commands through `shared/player.js` (the same code the client predicts with), one per tick plus an 8-command bank, repeating the last one when lost beyond redundancy. Snapshots every tick: own state in full (raw `PlayerState` bytes; the `WeaponState` as a bitmask of its non-zero fields and those f64 values, bit-exact and far smaller), other players delta-compressed against the client's last ack (`SnapshotRing`, 32 deep), the breakable mask, the doors' states (v11, see Doors), then the tick's events (world impacts except the receiver's own, blood hits, and kills repeated for `KILL_REPEAT_TICKS`). `INFO` (names/teams) every second and on roster changes.
  * **Prediction/reconciliation (client/main.js):** the client stores its state after every command; each snapshot's own state is compared byte-for-byte with the prediction for `lastCmd`; on mismatch it adopts the server state, replays later commands and blends the visible correction away (`smooth`, 15/s). Respawns are adopted the same way. Must stay bit-exact: `test/server.test.js` checks it through the wire with packet loss; the HUD shows the live exact rate.
  * **Interpolation:** other players render `INTERP_TICKS` (2 = CS:GO `cl_interp_ratio 2`) behind a smoothed server clock, lerped between the two bracketing snapshots. They are drawn as animated models (Phase 8d).
  * **Hits and lag compensation (`shared/hitgroups.js`):** four CS:GO hit groups (head ×weapon headshot multiplier, chest 1, stomach 1.25, legs 0.75) as yaw-rotated boxes that squash when crouching. The server keeps 64 ticks of position history and rewinds every target to the shooter's `viewTick` before tracing (`sv_maxunlag` 1 s); the nearer of world and player wins. Damage is truncated like CS:GO; friendly fire is off; the dead respawn after 2 s. The client stops its own bullets at the players it sees but shows hits only when the server's blood events arrive. Hidden tabs keep applying snapshots/events from a timer.
* **Damage (Phase 7a, `shared/player.js`):** `resolveShots` ports CS:GO FireBullet/HandleBulletPenetration: up to 4 penetrations, none beyond 3000 units, TraceToExit within 90 units, loss = 16% of damage + (3 / weapon penetration × 1.25) × (3 / combined modifier) + thickness² / (combined × 24); glass/grate 3.0 (5%), wood-wood/cardboard 3.0, plastic 2.0; range falloff compounds per hit; bullets go through players (12 units of flesh) for collaterals. Surface types (`shared/surfaces.js`) come from CS:GO `surfaceproperties_cs.txt` values via a GoldSrc RecursiveLightPoint face lookup → texture → `shared/materials.js` class. `applyDamage` is CS:GO armor (ratio × 0.5, bonus 0.5, helmet for the head, legs unprotected) plus tagging (`PS_VELMOD`, the weapon's flinch value, recovering 0.4/s — the rate is an approximation; SMGs have 0 = no tagging in the data).
* **Rounds and economy (Phase 7b):** `shared/economy.js` holds CS:GO competitive rules (15 s freeze, 1:55 rounds, 20 s buy time after the freeze, 7 s round end, $800 start / $16000 cap, $3250 win, loss bonus 1400 + 500/streak to 3400 with the 2019 decrement-on-win rule, weapon kill awards, −$300 teamkill), the buy menu and buy zones (`func_buyzone`, else around team spawns). `server/game.js` runs warmup (free respawns, $16000) until both teams have players, then freeze → live → over; survivors keep gear (guns reloaded), the dead start with knife + pistol; time expiry wins for CT on bomb maps, T on hostage maps, draw elsewhere; halftime swap after 15, first to 16. Freeze masks input with `FREEZE_BUTTONS` on both sides (prediction). `Game` takes a rules override (tests use short timings or `{ rounds: false }`). Client HUD: `client/hud.js` (B buy menu, Tab scoreboard, money, round bar/banner). The buy menu is CS:GO's radial wheel in print (SVG in a full-screen layer): a ring of the six `BUY_MENU` categories around a center showing the money; picking one turns the ring into that category's items our team can buy (`forTeam`), each sector with its price in red (OWNED / FREE), hatched when it cannot be bought now; the center shows the item under the mouse with its price and stats (damage, rounds/min, magazine, kill award) or why buying is not possible. The mouse's direction from the center picks a sector anywhere on the screen, the hovered one turns yellow and pushes out; a click opens or buys, a right click or a click in the center goes back; number keys pick (0 = the tenth); B / Esc close; a buy closes it and takes the mouse back. While it is open the mouse is the menu's, but movement and the other held binds keep working (not the fire buttons; `Input.keepKeys`), so buying on the move works. Refreshed every frame, touching the DOM only on changes.

* **Sounds (Phase 7d):** all synthesized (`client/audio.js`): per-class gunshot voices (pistol, heavy, SMG, rifle, sniper, shotgun, MG, silenced), mechanical clicks, footsteps by surface (texture material: soft, metal, wood, hard; in water at the feet a cartoon "splish", deeper than the knees a bigger "sploosh": a band-pass noise sweeping down from bright to dull with two or three rising sine bubbles, `Sounds.splash`, ~5 dB over a dry step; water / slime / lava from `pointContents`, so de_aztec's river and `func_water` both count, for us and other players; landing in water splashes big), landings, knife swishes, hit thwacks and the headshot ting, bullet impacts, grenade bounces, flashbang bangs with a ringing ear and the world muffled for the blindness, smoke hiss, fire crackle, decoy fake shots, explosions, the C4 beep. Positional: stereo pan from the view, distance falloff, a low-pass far away, behind, and when a wall is between (one trace). `client/soundscape.js` decides when: our predicted weapon events (reload clicks timed like the first-person animation), running footsteps (walking and crouching are silent, as in CS:GO), and other players from snapshots (shot counter, reload bit, movement speed).

* **Models (Phase 8c, toolkit for 8d-8f):** low-poly, flat, few colors (see the art style above), built in code at load.
  * `client/gl/meshkit.js` `MeshBuilder`: box, rbox (every edge rounded: a grid on the faces pushed onto the rounded surface), sphere, slab (rounded vertical edges), lathe (about z), capsule, extrude (side outline along y), loft (z sections) under a transform stack (translate / rotate with GoldSrc angles / scale), and `mirror` (flips winding, swaps bones through `Skeleton.mirror`); `bevel(r)` rounds the next boxes (a chamfer) and extrusions (45° cut, the outline inset on the faces). Every primitive is closed and wound counter-clockwise from outside. Normals are smooth within a primitive across edges flatter than its crease angle (`smooth(deg)`, 50° by default, 0 = faceted; weighted by corner angle × area), so round parts shade round and the composite inks no crease on them, while box corners stay sharp; separate primitives never blend. The flat faces of bevelled boxes and outlines are hard: they keep their own normal, and the bevels bend from one face's normal to the next (rounded edges on flat sides that still print flat, which the shine needs). `sweep(sections, seg, up, ends)` sweeps a tube along a path of oval or rounded-box sections (superellipse exponent `n`) square to the path, with round or flat ends: torsos and limbs in one piece. `skin(fn)` skins the next vertices by position: fn returns two bones and the second's weight (mirrored halves remap both), so a limb tube blends across its joints. * **Comic print (Phase 12):** a deferred renderer.
  * **G-buffer** (`client/gl/gbuffer.js`): three color targets plus depth: albedo + light (0..1) and normal + object id in RGBA8, then `DEPTH_NEAR` / linear depth as a half float + flags (RG16F; where `EXT_color_buffer_half_float` is missing, `DEPTH_PACKED` in every shader via `shaderDefines` in `program.js`: 24 bits of an RGBA8 decoded at every fetch) (`G_FLAGS`: `FLAT` unshaded, `SKY`, `SCREEN` see-through, `VIEW` the first-person view, `CHAR` characters: players, hostages and their guns; `SkinnedRenderer.flags` adds flags to every pixel of its draws). Every scene shader writes all three through `GBUFFER`'s `gbuffer()` (`client/gl/shaders.js`; `test/comic.test.js` checks it). A frame: `Renderer.begin` (clear to sky), `render` (world, sky, overlays with `draw(viewProj, gbuffer)`), the first-person view after a depth clear, then `composite` to the canvas; the flashbang afterimage and the crosshair come after it.
  * **World** (`WORLD_FS`): per `MAT` class a flat color (lifted `pow 0.8` and saturated 1.25 from the original averages) with sparse ink marks that fade with distance and with screen size (`grid` / `line` use `fwidth`), weathering blotches on floors only. Light = the lightmap's lifted brightness over the map's own fully lit level (`fullLight`: the 75th percentile of its lit texels, measured at load, shared with models as `mapLight.full`), `pow 0.8`; colored light tints the albedo. Ids 1..127 from the texture seed and the entity slot, so ink follows texture changes, never BSP splits. Glass and water are a 15° dot screen of opaque pixels (coverage = alpha, flag `SCREEN`: no ink against what lies behind); water draws drifting contour lines. Fullbright faces are `FLAT`. Mappers lay func_walls, func_illusionaries and water flush on world faces or on each other, which z-fought (de_train's roofs): brush entity faces (`FLAG_ENTITY`) are drawn a hair nearer than the world, and alpha-tested, breakable and moving ones nearer than other entities' (a constant clip-space offset in `WORLD_VS`, ~25 depth steps a level); alpha-tested textures with no opaque pixel (`{blue`, `{wallinv*`: invisible blockers in GoldSrc) are not drawn. The opaque bulk draws with `WORLD_SOLID_FS` (WORLD_FS with `SOLID` defined: its `CUT` is no `discard`), alpha-tested faces (`{` textures: foliage, grates) from their own index range after it and see-through ones with WORLD_FS: a shader that merely contains a discard kept the GPU from skipping hidden pixels before shading them (de_dust2, with no alpha-tested face at all, drew its world ~20 % slower).
