# Project Overview: ComicStrike, a Procedural Web FPS

**Concept:** A lightweight, high-performance web-based multiplayer FPS. It combines the advanced mechanical logic and physics of CS:GO with the simplified geometry of classic CS 1.6 maps, rendered as a procedural comic print: flat colors, ink lines and halftone dots.

**Design Philosophy:** Built through first-principles engineering, the project utilizes a zero-dependency, self-contained architecture. The client executes directly in the browser via standard ES Modules—requiring no npm packages, bundlers, WebAssembly, or third-party graphics libraries. Every system is micro-optimized to eliminate garbage collection spikes, minimize input lag, and maximize frame rates.

## 1. Technical Stack

* **Language:** Vanilla JavaScript (ES6 Modules) and standard Web APIs.
* **Graphics:** Pure WebGL2 (Bare-metal rendering).
* **Networking:** WebTransport (HTTP/3 QUIC) for native UDP-like datagram transmission.
* **Map Format:** Direct GoldSrc BSP (Version 30) binary parsing.

## 2. Core Systems & Architecture

### Graphics & Rendering (The Comic Print)

* **Zero-Asset Pipeline:** The game loads exactly zero image or texture files.
* **Procedural Fragment Shaders:** The visual identity is a comic book: flat colors with sparse ink marks per surface class (some bricks outlined, plank seams, tile grout), shade printed as halftone dots, ink outlines on every silhouette, crease and part. Surface classes come from texture names (e.g., `metal`, `crate`) extracted from the map file; colors from the original textures' averages.
* **Single-Draw-Call Geometry:** Map geometry is packed into a single Vertex Buffer Object (VBO) to keep GPU draw calls as close to zero as possible (the opaque bulk in one draw with a shader that never discards, alpha-tested faces in a second: see Comic print, World).
* **One Print Pass:** everything draws into a G-buffer, then an ink pass at the G-buffer's resolution and one fullscreen composite shader print the frame (see Comic print).

### Map Parsing (GoldSrc BSP)

* **Native Binary Reading:** Native `fetch()` and `DataView` APIs are used to read CS 1.6 `.bsp` files directly into JavaScript `Float32Array` and `Int32Array` buffers.
* **Zero-Overhead Memory:** Because the parsed BSP lumps are already loaded into typed arrays, they are passed directly into WebGL2 buffers, bypassing the need for intermediate data structures or mesh conversions.

### Physics & Gameplay Logic (CS:GO Mechanics)

* **Modern Movement on Retro Geometry:** The engine implements CS:GO’s precise movement physics (acceleration, friction, air-strafing) mapped against the simplified collision hulls of CS 1.6 BSP architecture.
* **Strict Memory Management:** All game states, physics calculations, raycasting, and AABB collision sweeps are handled via pre-allocated `Float32Array` object pools to prevent JavaScript garbage collection from interrupting the main loop.

### Networking & Server Sync

* **WebTransport Datagrams:** Replaces WebSockets and WebRTC to provide a direct, low-latency connection without the overhead of STUN/TURN signaling servers.
* **Source-Style Netcode:** Utilizes fixed-tick server logic (e.g., 64-tick), client-side prediction, and server reconciliation, ensuring crisp hit registration that doesn't suffer from TCP head-of-line blocking.
* **Pragmatic Backend:** The server architecture remains lightweight enough to be deployed directly onto custom self-hosted Linux environments (such as DietPi setups or Pterodactyl panels) with minimal overhead.

* **Opening a .bsp in the editor (`client/editor/decompile.js` `decompileBSP`, run in the compile worker after `parseUntrustedBSP`):** a compiled map keeps no brushes, but every path down a model's hull 0 tree that ends in a solid leaf is a convex cell bounded by the node planes along it. Each model's tree is walked with a convex cell (face polygons, each split at the node planes; the world's starting cell is the empty leaves' bounds 32 units out, since GoldSrc's void is solid and the map would otherwise be buried in blocks), and solid, sky and water leaves become shapes: neighbors joined wherever the union is convex (`join`: every vertex of each behind every other plane of the other, no texture disagreeing on a shared plane; dust2 1,539 cells → 1,302), an axis-aligned cell on whole units with one texture round its sides a Box, the rest convex pieces. A cell side on a node takes the texture of that node's face (on the matching side) under its middle, else near a corner, else of any face of the model on the same plane facing the same way under it (a compiler hangs a face on one of the nodes sharing its plane, so the node that cut the cell may hold none), else the nearest of those, a wall before any sky (that side was hidden in the original); sides with no face on their plane get none. A side left without a texture compiles to no face: a hole in a wall to see through (de_dust2 came back with 1.2 % of its walls missing, now none). A leaf whose side lies over both sky and wall faces (brushes the tree merged into one leaf: a wall top half sky, A long's door wall) is cut along the sky face's edge, square to the side, until each side is over one or the other (`byTexture` / `divide`); before, the whole side took the sky and the wall showed the sky through it (0.65 % of de_dust2's wall hits, 1.2 % of cs_office's). Sky leaves keep a wall face's texture where one lies under their side (mappers run walls up into sky brushes). * **Performance (Phase 11c):** hot paths (every frame, every tick) allocate as little as possible. Measured traps in V8: `Math.hypot` is a builtin call that allocates its result (hot client code uses `Math.sqrt` of the squares; shared simulation code keeps `hypot` for bit-exact results); typed-array `subarray` makes a view object (copy with index loops); floating-point arguments to a function that is not inlined are boxed on every call (the recursive hull trace passes its arguments through a preallocated per-depth stack, `ARGS` in `shared/trace.js`; the limb solver writes its math out); array or object literals, closures and template strings built every frame (hoisted, reused, or rebuilt only when their inputs change: the HUD's round bar and banner, the spectator notice, the radar font). Measure allocations with V8's sampling heap profiler from Node (`node:inspector` `HeapProfiler.startSampling` with `includeObjectsCollectedByMajorGC/MinorGC`; the server and client/anim modules run under Node as they are, with Math.random seeded for repeatable runs), and in the browser by summing heap rises (`performance.memory`) while stubbing subsystems. 5v5 numbers: server ~0.14 ms and ~17 KB per tick with 10 bots; client ~11 KB per frame with 9 animated players (was ~37). Measured again (a headless 10-bot de_dust2 game, 2000 ticks after a forced GC, 256 MB semispace): the whole server allocates ~1 KB a tick, the bot brain's small result objects included (V8 elides most of them), so nothing is left worth the code there; WebGL uniform calls remain.

Timing every pass (~15 queries a frame) itself slows a GPU near its limit: at 2560×1440 ×1.2 on the Iris Xe, 59 → 42 fps with `cl_showfps 3` on. So with it off one query covers the whole frame (`light`), always: the frame's GPU time (`frameMs`) and how many frames old its result is when it comes back (`behind`; 2 at ease in Chrome, the readback's own delay, 4 on an overloaded GPU, whose frames the browser queues: mouse lag before any frame is late), both eased, for r_dynres, `cl_showfps 2` (`gpu 9.3 ms, 2.0 frames behind`) and the benchmark. At 60 fps an integrated GPU idles between frames at low clocks, so every pass reads ~3× its real cost; `r_drawrepeat 20` (not saved) draws each frame 20 times back to back, keeping the GPU at full clock (also on a hidden page, whose rAF otherwise runs at ~1 fps), and the readout is then per drawing. Compare variants by ratios to a pass they cannot touch, averaged over many readings: absolute levels still drift ~3× between runs. Never judge a saving at 60 fps: the GPU clocks down to fill the frame, so the other passes stretch by what was taken out (dropping the color clears read as nothing at 60 fps and was a fifth of the frame at `r_drawrepeat 20`). Three measures:
    * **Automatic resolution** (`client/dynres.js` `DynamicResolution`, `r_dynres`, off by default, Video: Automatic resolution): with GPU timings (the light query above) it keeps the GPU ahead of the frame, judged over windows of 0.5 s: a step of 0.05 down once the GPU takes over 80 % of the frame (`DOWN_SHARE`, of 16.7 ms or a slower display's interval; double over all of it or with late frames) or, busy over half the frame, its results come back 0.8 frames later than the lowest ever seen (`BEHIND_RISE`, the floor in whole frames), before any frame is late; a step up only after 3 s clean when the next scale's GPU time, growing with its pixels, is predicted under 60 % of the frame (`UP_SHARE`), so it never tries a scale that brings late frames back (a GPU at low clocks reads slow, which only makes going up later); a step down soon after a step up doubles the wait. Before (gaps only) it stepped down only after a stutter and probed up every 4 s into one, and never saw the queued frames. Where it settles (held 10 s) is kept per window size in localStorage (`comicstrike.dynres`, as a scale of the canvas), and the next map starts there instead of at full scale (a stutter at every map start). Its steps are 0.05 of the canvas whatever the most is (`dynres.most` = mat_viewportscale; the factor is of the most). Without timings (some browsers) the old way, from the gaps between frames alone: windows of 0.5 s with over 8 % slow frames take the scene's render scale a tenth down, to half the canvas (`mat_viewportscale` sets the most), and once there the print's own resolution (the canvas, `print`: 0.85, then 0.7, stretched by the browser, for a GPU where the print itself is the cost: on the user's laptop the print was 40 % of the frame on de_cache); 4 s with no slow frames tries a step up (the print back first, then the scene by 0.05), and a try that brings slow frames back within 3 s steps back and doubles the wait (to 64 s); 1 s between steps, stalls over 250 ms ignored, 2 s of grace after a map load (both ways). Resizing the G-buffer costs no visible hitch (measured again with the benchmark: nine `mat_viewportscale` steps in 12 s at 1024×768, the G-buffer and the ink target reallocated each time, 60.1 fps, 0 % slow frames, worst frame 17.5 ms, no hitch; so the targets are not allocated once at the largest size and drawn into a viewport, which would have put a clamp on every print fetch for nothing).     * **Split resolution (Phase 13c):** the render scale (`mat_viewportscale`, r_dynres, `Renderer.resize`) sizes only the G-buffer; the canvas stays at the page's pixels (times `r_hidpi`) and the print runs over every canvas pixel, reading depth, normal and flags from the texel under it (`u_gscale`, the line spacing scaled into texels) and the color plate filtered between texels (`texture` on target 0, `LINEAR`; a plain `texelFetch` at scale 1), so the ink lines, dots and crosshair stay pixel-crisp while the world, models and view draw fewer pixels; the ink follows the texel edges, so at 50 % a diagonal line steps by 2 px.     * **Ink pass (Phase 14b):** the ink (`INK_FS`: silhouettes, creases, object lines, the far characters' rings, all the neighbor fetches) runs over the G-buffer's texels into an R8 target (`GBuffer.ink`, LINEAR), and the composite reads it under each canvas pixel: texel for texel at the canvas's own size (pixel-identical to the one-pass print), filtered between texels at any other render scale. So below 100 % the ink's staircase (2 px steps at 50 %) becomes a smooth ramp, the ink's anti-aliasing, and the fetch-heavy part costs the scene's pixels, not the screen's: at 50 % a quarter (on the user's laptop the print was 59 % of a 3 ms frame at res 50 %, 1.8 ms that the scene scale could not touch). The composite is left with three fetches a pixel (albedo, depth and flags, ink) and the dots. `mat_viewportscale` (2 by default since Phase 14p: 4× the pixels; r_dynres, when turned on, takes it down where the GPU cannot keep up; up to 8; Video: over 1 supersamples): the color plate and the ink are then filtered down from more texels (at exactly 2 a 2×2 box; over 2 through their mipmaps: `GBuffer.resize` allocates the chains, `buildMips` after the ink pass, and the composite reads both with `textureLod` at log2 of the scale, a box filter over the texels under each pixel, since LINEAR alone read 4 of them and aliased), smoother edges and lines for a GPU with room; the scale is capped by the GPU (`clampScale` in renderer.js: the largest texture side and `r_supersample_max` 64 Mpx; 5× of a 1440p window would be 92 Mpx, ~1.4 GB of targets; `cl_showfps 2` says "capped"; `test/renderscale.test.js`); measured in the pane at 850×347 (60 fps readings, the GPU clocked down): 2× 5.9 ms, 3× 10.8, 6× 14.6; costs what it adds (print 0.30 → 0.81 ms at 150 % in a 604×347 pane). The dots (printed from the color plate after), the world's own ink marks (in the albedo) and the crosshair (drawn after) never pass through the ink target, so none is blurred. Measured at 1024×768, full clock: the print pass +10 % (1.02 → 1.12 ms per drawing, the ink pass unchanged), 0.25 % of the pixels changed, all darker. A mode with no pass frees the targets (`ensure(AA.OFF)`: TAA's history at the default 2x of a 1440p window is ~300 MB), and `r_supersample_max` counts them (`aaBytes`: FXAA 1, SMAA 7, TAA 32 bytes a texel besides the G-buffer's ~15). * **File names vs ad blockers:** privacy filter lists block some script URLs by name (`hitbox.js` was blocked as an analytics tracker, freezing the client on load). Avoid names like `hitbox`, `analytics`, `track`, `ads`, `beacon`, `stats` in client-served files.
* **Layout:** `shared/` = code run identically by client and server (BSP parsing, physics, protocol); `client/` = browser only; `server/` = Deno only.
* **Lighting:** the BSP's own lighting lump is packed into one lightmap atlas texture at load time (map data, not an image file; at most `ATLAS_MAX_H` 8192 rows, faces past it lit by the grey block: a crafted map's faces can share one block of light while each asks for its own rectangle); albedo is fully procedural.
* **Textures (Phase 8b):** surfaces stay flat and simple: the name class patterns of `shared/materials.js` (cheap, flat, few colors), colored like the originals. `tools/gen_texturedata.js` measures every miptex in `wads/` and every texture embedded in `maps/*.bsp` (`tools/wad.js`, `tools/texanalysis.js`, one worker per core, a few seconds) and writes `client/texturedata.js`: per texture name, the main surface's average color (color bands such as a wainscot or trim strip and transparent texels left out) and whether the original repeats in lines. That is 4 bytes each for about 5,800 textures, ~90 KB, no pixels. `client/texcolors.js` `withOriginalColor` applies it in `client/mapmesh.js`: the original color replaces the name-guessed one, and brick/tile patterns become plain where the original has no repeating lines (brown plaster named like brick). Unknown names keep the name classes. Rerun the tool after adding WADs or maps with embedded textures. Only GoldSrc texture names (`TEXTURE_NAME`) are kept (`readMiptex` in tools/wad.js): the names go into a quoted string of texturedata.js, where a map's texture named with a quote was code every page ran. A richer fitted model (noise spectra, grids, bands) was tried and dropped as too heavy and too busy for the art style.

* **Netcode (Phases 5-6):** `shared/protocol.js` is the binary wire format (v22; preallocated `Writer`/`Reader`, every message ≤ `MAX_DATAGRAM` 1024). Client → server: `HELLO` (resent every 250 ms until `WELCOME`, which is looked for every 10 ms (`JOIN_POLL_MS`: practice answers within a tick, and waiting the 250 ms first was a quarter second off every start); v14: it names the room, see Your own maps and rooms), then `CMDS` every tick with the newest 4 user commands (redundancy) plus the snapshot ack; each command carries `viewTick`, the server tick the player was seeing others at, and a pitch the server holds to ±89 as clients send it (`readCmds`: a pitch of 1000 threw a grenade at ~4,700 u/s). * **Models (Phase 8c, toolkit for 8d-8f):** low-poly, flat, few colors (see the art style above), built in code at load.
  * `client/gl/meshkit.js` `MeshBuilder`: box, rbox (every edge rounded: a grid on the faces pushed onto the rounded surface), sphere, slab (rounded vertical edges), lathe (about z), capsule, extrude (side outline along y), loft (z sections) under a transform stack (translate / rotate with GoldSrc angles / scale), `warp(fn)` (moves each corner by position before its normal is taken: a lumpy cloud out of a sphere) and `mirror` (flips winding, swaps bones through `Skeleton.mirror`); `bevel(r)` rounds the next boxes (a chamfer) and extrusions (45° cut, the outline inset on the faces). Every primitive is closed and wound counter-clockwise from outside. Normals are smooth within a primitive across edges flatter than its crease angle (`smooth(deg)`, 50° by default, 0 = faceted; weighted by corner angle × area), so round parts shade round and the composite inks no crease on them, while box corners stay sharp; separate primitives never blend. The flat faces of bevelled boxes and outlines are hard: they keep their own normal, and the bevels bend from one face's normal to the next (rounded edges on flat sides that still print flat, which the shine needs). `sweep(sections, seg, up, ends)` sweeps a tube along a path of oval or rounded-box sections (superellipse exponent `n`) square to the path, with round or flat ends: torsos and limbs in one piece. `skin(fn)` skins the next vertices by position: fn returns two bones and the second's weight (mirrored halves remap both), so a limb tube blends across its joints. Vertices are 24 bytes: position, normal, the heavier bone, color + finish (`FINISH`: cloth, skin, metal, polymer, wood, pattern, and the gun looks' camo, stripes, hex, fade; `finish(rgb, f)` makes a color that carries one, `defaultFinish` for the rest), the second bone and its weight, a pattern coordinate (the fade's place along a gun; read with the bones as one 4-byte attribute).

The cartoon shading (see Comic print, Models) is two flat tones split by a crisp terminator, times the map light at the model: `SurfaceMap.lightAt` (GoldSrc R_LightPoint: the lightmap texel of the first face below) lifted by `modelLight` like the world shader.
